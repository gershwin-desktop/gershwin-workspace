# Referee report 2026-10-11 - Workspace against the Mac OS X 10.6.8 Finder

The Referee compares and reports; nothing was fixed. Oracle: Users-Mac-mini.local, Finder 10.6.8, driven with Tools/mac-oracle (finder-set, finder-get, shot, UI scripting, push, pull). Our side: libDSStore, libGSMetadata and libFSNode as installed in /System (dev e8cf0c07), plus the Workspace-side classes (DSStoreInfo, GWViewSettingsManager, GWMetadataCopier, FinderInfoModel, GWMetaArchive) compiled from the dev sources into a small writer/reader tool (own Xvfb, never :0). The tool calls what Workspace calls: GWViewSettingsManager readSettings/writeSettings, FinderInfoModel (what the Inspector uses), GSFileMetadata, FSNAlias, FSNLocationFile, GWMetadataCopier, GWMetaArchive. The tool source is scratch and not committed.

Method per row. Forward: Finder writes (finder-set, UI scripting, AppleScript, NSWorkspace) then flush, pull, our reader. Reverse: our writer, push (tar plus dot_clean, so sidecars become native xattrs), then finder-get and shot. Cooperative: Finder-written records load and save through our code, decoded stores and sidecars compared (independent reader dsread).

Legend: PASS, FAIL, n/a (cannot be tested or does not exist on 10.6), - (not covered).

## Answers to the coordinator's questions

- (a) Where does 10.6 Finder keep a label? Only in FinderInfo fdFlags bits 1-3 (Finder colour number 1 gray, 2 green, 3 purple, 4 blue, 5 yellow, 6 red, 7 orange; AppleScript label index 1 orange, 2 red, 3 yellow, 4 blue, 5 purple, 6 green, 7 gray). It writes NO lclr record in any .DS_Store (checked in the own stores of f3 and the HFS+ image, and the parent stores) and IGNORES a lclr record: seven files with lclr 1..7 and no FinderInfo all read label index 0 after a push (case rl).
- (b) Does Finder's own .mailtoloc keep its extension despite fdFlags 0x0010? Yes. Finder reports name "mail.mailtoloc", displayed name "mail.mailtoloc", `name extension` empty, extension hidden true; the same query on a .webloc gives displayed name "ex", extension "webloc". 10.6 does not know the .mailtoloc extension, so the hidden-extension flag has no effect there.
- Does Finder's Compress of a single folder carry `__MACOSX/._folder`? Only when the folder itself has FinderInfo (a label): a labelled folder gave `__MACOSX/._proj` (82 bytes) from Finder, none from `ditto -c -k --sequesterRsrc --keepParent`. An unlabelled folder gets none from either. Finder additionally zips the folder's own .DS_Store (and its `._.DS_Store`). Our extractor strips the top folder and does not apply that `._proj` (OPEN-1 stays as designed).

## Mismatches, with repro

M1 Locked is the BSD uchg flag on Finder; Workspace models kNameLocked.
Repro forward: on the Mac `finder-set <case> locked@c.txt true` (E18: file gets uchg, FinderInfo unchanged), pull; the tar and the sidecar carry nothing; `gwi meta-read c.txt` gives locked=0, namelocked=0.
Repro reverse: `fim nl.txt namelocked=1` (FinderInfoModel; FinderInfo fdFlags 0x1000), push, `mac-oracle finder-get rm3 locked@nl.txt` gives false; E18 already showed Finder renames such a file. On Linux the Inspector's real Locked uses an immutable flag that no archive or sidecar carries.

M2 A comment written only as the com.apple.metadata:kMDItemFinderComment xattr or in the sidecar (GSFileMetadata finderComment, writeToFileAtPath / writeSidecar) is not shown by Finder 10.6.
Repro: `gwi meta-write comment.txt comment=hello sidecar=1`, push, `finder-get comment@comment.txt` gives an empty string although the xattr (60 bytes) arrived. With a cmmt record in the folder's own .DS_Store (alone, or with the xattr) Finder shows it. The Inspector path (FinderInfoModel comment) writes both and passes (rm3).

M3 A .mailtoloc written by FSNLocationFile has no FinderInfo type ilma and creator MACS, so 10.6 Finder lists it as "Dokument" (document file), not as an internet location.
Repro: `gwi webloc mailto:a@example.com <dir>`, push, `get {name, kind} of every item`: kind Dokument. The .webloc and .ftploc written the same way are internet location files with the right location. Finder's own file has FinderInfo ilma/MACS 0x0010 and a resource fork (drag, TEXT, url).

M4 The quarantine value in a `._` sidecar made by 10.6 tar for a flag 0000 value carries a "q/" prefix, and GSFileMetadata passes it through.
Repro: on the Mac `xattr -w com.apple.quarantine '0000;4e8f1c2a;Safari;' f`, `mac-oracle pull`; `gwi meta-read f` prints quarantine=q/0000;4e8f1c2a;Safari;. Pushing it back restores the plain 21-byte value (so the round trip is lossless, but anything on Linux that parses the value sees the prefix).

M5 Custom icons Finder writes contain is32/il32/it32 and JPEG 2000 ic08/ic09; NSImage from `customIconAsImage` has 16, 32, 128 px representations only.
Repro: `gwi icon-image pull/m1/icon.txt` on a Finder icon set from a 256 px PNG with NSWorkspace setIcon.

M6 Cooperative load and save is not byte for byte: saving a folder through GWViewSettingsManager adds legacy `.` records (BKGD, bwsp, fwi0, fwsw, iarr, icsp, icvo, icvp, lblp, or lsvp) to the folder's own store, which Finder ignores (E2); entries for files that are not in the directory are pruned; a store with only the legacy LSVO/lsvo/lsvt triple Finder wrote (E8 m_lcv) gets a new lsvp (Finder prefers lsvp, E10); a hand-made BKGD ClrB (Finder ignores it, E12 b7) becomes an icvp with that colour, which Finder honours (the folder turns from white to red); hand-made lsvp with integer sizes and viewOptionsVersion 1 are rewritten as reals and version 0. Finder-written records (bwsp, icvp, lsvp, vstl, Iloc with its trailing bytes, cmmt, dilc) were all preserved, decoded equal.
Repro: copy any Finder parent store to `<root>/.DS_Store`, `gwi view-roundtrip <root>/<folder>`, compare `dsread` of both stores.

M7 GSFileMetadata setCustomIconData on a directory silently writes the icon fork into `._folder`; 10.6 cannot unpack a resource fork onto a folder.
Repro: `gwi meta-write iconfolder icon=x.icns sidecar=1`, push: tar reports "copyfile unpack (./iconfolder) failed: Operation not permitted", the push exits with failure and the folder shows the generic icon. The Inspector path (Icon CR file plus FinderInfo 0x0400) works (rm3 shot).

M8 Sidecars not merged by three Mac copy tools: plain `unzip` leaves `__MACOSX` in place; `ditto <dir> <dir2>` and `cp -R` of a folder holding Linux-made `._` files drop them without applying anything (xattrs empty afterwards); `tar -x`, `dot_clean` (with and without -m), `ditto -x -k` and Finder double click apply them. Mac behaviour, no Workspace change possible, relevant for users.
Repro: tar a folder with `._x` files, extract with COPYFILE_DISABLE=1, then `ditto` or `cp -R` into a new folder and `xattr -l`.

M9 Info only: `GSFileMetadata metadataFromAppleDoubleData:` followed by `appleDoubleData` drops attributes it does not model (org.example.*, com.apple.TextEncoding) and zeroes the ATTR debug tag (quar.txt 213 to 175 bytes). The paths Workspace uses (writeSidecarToFileAtPath, GWMetadataCopier copy, GWMetaArchive) keep them byte for byte; on ext4 load and save moves small attributes from the sidecar into user.* xattrs and deletes the sidecar, forks above the xattr size stay in the sidecar.

## Addendum: quarantine value in a sidecar needs the "q/" prefix (M4 follow-up)

Steps: four hand-built compact `._f` sidecars (entry 9 with 32 zero FinderInfo bytes, ATTR block with one attribute com.apple.quarantine, entry 2 of length 0; ATTR offsets are absolute file offsets) with the value plain `0000;4e8f1c2a;Safari;`, prefixed `q/0000;4e8f1c2a;Safari;`, plain `0002;...` and prefixed `q/0002;...`. Pushed by tar -x, and by COPYFILE_DISABLE=1 tar -x followed by dot_clean -m. Read with `xattr -p com.apple.quarantine`.

Observed (identical for both routes): plain 0000 gives NO attribute; `q/0000;...` gives `0000;4e8f1c2a;Safari;`; plain 0002 and `q/0002;...` both give no attribute (non-zero flags are dropped, as in E16).

Answer: yes, 10.6 needs the `q/` prefix in a sidecar; it is the form copyfile itself packs, and an unprefixed value is silently dropped. Our M4 passthrough is therefore correct and must not strip the prefix when writing; only a flag-0000 value survives either way. The Mac was reset afterwards.
